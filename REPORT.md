# CI/CD Pipeline Security Auditor — Project Report

## Outcome and evidence boundary

Completed a working offline auditor in Python with nine finding rules, directory scanning, terminal/JSON/SARIF output, severity-based exit codes, vulnerable and corrected fixtures, automated tests, and a GitHub Actions workflow. This report records local Windows verification on 15 October 2026. The project has not been published and no hosted GitHub Actions run, merge restriction, or production deployment is claimed.

## Objective and threat model

The project examines configuration mistakes that can expose credentials, introduce mutable build dependencies, turn pull-request text into shell code, or give untrusted work excessive privileges. Inputs are local configuration files; they are treated as untrusted data. The auditor does not execute YAML commands, validate live credentials, clone repositories, or contact providers during a scan.

The portfolio demonstration follows a repeatable sequence: inspect the vulnerable file, run the scanner, review the exact finding and remediation, then scan a corrected file. The evidence is generated by those local runs. The vulnerable fixtures are simulations, not observations of a real compromise.

## Implementation

1. Discover explicit files or YAML files recursively within supplied directories. The default target is `.github/workflows`; environment directories, Git metadata, and node_modules are skipped. Symlink files/explicit targets are rejected and symlink directories are not traversed.
2. Read at most 2 MiB per file as UTF-8, accepting a UTF-8 BOM.
3. Parse YAML into source-marked nodes without constructing Python objects. Retaining nodes also avoids treating GitHub’s `on` key as a Python boolean. Reject duplicate keys, aliases, merges, custom tags, multiple documents, excessive nesting, and common malformed workflow structures.
4. Apply secret heuristics and, in GitHub mode, inspect workflow/job permissions, external references, shell scripts, trigger combinations, and runner labels.
5. Produce locations, severity, rule ID, title, and remediation without embedding source values. A block-scalar finding points to the YAML field introducing the script, rather than claiming an exact shell token location.
6. Exit 0 below the selected threshold, 1 when findings meet it, or 2 when processing is incomplete. `--fail-on none` never suppresses processing errors.

## Detection rules

| Rule | Severity | Detection and interpretation |
| --- | --- | --- |
| SEC001 | High | Sensitive field names, inline assignments, selected GitHub/AWS token formats, and private-key headers suggest a hardcoded credential. Empty values and common complete variable/secret references are excluded. This does not establish validity or compromise. |
| PIN001 | Medium | An external action or reusable workflow lacks a full 40-hex commit reference. Local action paths are handled separately. |
| PIN002 | Medium | A Docker action lacks a sha256 digest reference. |
| INJ001 | High | Selected untrusted event/inputs expressions appear directly in a run script. Literal bracket property access and whitespace variants are normalized; expressions are never evaluated. |
| PERM001 | High | Workflow/job requests write-all token permissions. |
| PERM002 | Medium | Explicit write grants to selected sensitive token scopes require review. Legitimate OIDC/deployment grants can trigger this policy warning. |
| PERM003 | Low | Workflow-level permissions are implicit. The auditor cannot determine repository defaults offline. |
| TRUST001 | Critical | pull_request_target/workflow_run coincides with an actions/checkout ref or repository explicitly derived from pull-request context or refs/pull paths. |
| RUN001 | Medium | A pull-request-triggered workflow contains a literal self-hosted runner label. Actual runner access restrictions are unknown. |

No rule downloads an action or verifies the trustworthiness of a pinned commit. GitHub documentation also describes stronger dependency controls; this project implements an explicit SHA-pinning policy, not a complete supply-chain guarantee.

## Lab results

| Input | Mode | Findings | Exit | Evidence |
| --- | --- | ---: | ---: | --- |
| examples/insecure.yml | GitHub | 4 | 1 | reports/insecure.json |
| examples/secure.yml | GitHub | 0 | 0 | reports/secure.json |
| examples/advanced-insecure.yml | GitHub | 7 | 1 | reports/advanced-insecure.json |
| examples/advanced-secure.yml | GitHub | 0 | 0 | reports/advanced-secure.json |
| examples/generic/gitlab-insecure.yml | Generic | 1 | 1 | reports/generic-insecure.json |
| examples/generic/gitlab-secure.yml | Generic | 0 | 0 | reports/generic-secure.json |
| .github/workflows | GitHub | 0 | 0 | reports/ci.json |

The basic fixture flags write-all, an action referenced by main, a fake hardcoded deployment password, and a pull-request title interpolated into a script. Its corrected pair uses read-only permissions, a reviewed full action SHA, a secret reference, and a quoted environment-variable expansion.

The advanced fixture produces seven findings: sensitive write permission, self-hosted PR runner, two mutable external references, mutable container image, untrusted script interpolation, and privileged checkout of PR-controlled code. The corrected pair switches to an unprivileged pull_request trigger and hosted runner, narrows permissions, pins checkout, and handles input as data. The unnecessary external reusable workflow and container are removed rather than replaced by invented trusted dependencies.

The generic pair demonstrates only secret heuristics on a GitLab-shaped YAML file. It does not establish platform-specific GitLab security. No real secret is included in any example.

## Testing and verification

39 unittest test methods passed on the final implementation. Subtests exercise additional variants. Coverage includes branch/tag/short-SHA references; local actions; reusable workflows; image digests; literal credentials and safe references; private-key headers; ignored comments; direct, whitespace, and bracket-expression injection; environment-variable mitigation; permissions; secret inheritance; privileged checkout; self-hosted runners; source locations; report redaction; and generic coverage labels.

Input/CLI tests cover malformed YAML, unsafe tags, aliases, duplicate keys, merge keys, multi-document files, nesting/size limits, UTF-8 errors/BOM, malformed jobs/steps, missing inputs, empty directories, directory exclusions/deduplication, partial failures, thresholds, JSON/SARIF structure, default targets, and input/output collision protection. Parser diagnostics deliberately omit source snippets to avoid printing credential-bearing input.

`python -m pip check` reports no broken requirements. The captured SARIF report parses as JSON and its key fields/results are tested; external SARIF schema validation and a GitHub SARIF upload were not performed. The CLI’s intended gate behavior was tested locally, including failures for vulnerable fixtures and success for corrected fixtures. Tests were run on Windows; the hosted Ubuntu runner remains untested.

Raw test output is saved in reports/tests.txt. reports/execution-log.json records commands, expected and observed exit codes, stdout, and stderr. reports/manifest.json records the interpreter/dependency versions and SHA-256 hashes of source, tests, fixtures, dependency file, and active workflow for this evidence set.

## CI integration and operational use

The supplied workflow has read-only contents permission, disables checkout credential persistence, uses full action commit pins, sets a timeout, runs tests, audits active workflows, and verifies corrected examples. Vulnerable examples remain under examples/ and are never installed as active workflows. Verified pins are checkout v4.2.2 and setup-python v5.6.0; pinning is not a claim that these versions are the latest.

To enforce this after publication, run the workflow in GitHub and configure the job Audit and regression tests as a required check. Protect changes to the scanner, tests, and workflow through repository review/rules; a contributor able to alter enforcement code could otherwise weaken the check. Passing this check alone does not guarantee that a later production deployment is protected. Deployment ordering, repository rules, and independent security controls must also enforce the policy.

## Limitations and interpretation

- Findings are heuristics/policy warnings, not exploit proofs. Some authorized write grants and synthetic passwords intentionally trigger alerts. Thresholds change failure behavior, not which findings are reported.
- Secret detection covers selected names/formats in parsed YAML values and inline assignments. It misses unknown token formats, encoded/assembled secrets, secrets in comments, Git history, external scripts, and values fetched at runtime. It never verifies a credential with its provider. Complete expressions containing literal fallbacks can evade the simple reference exemption.
- Injection analysis matches selected context expressions. It does not provide complete shell parsing, taint propagation through env/matrices/outputs, computed-property resolution, or analysis of all expressions/actions. Passing data through env still requires correct shell handling and avoiding eval.
- Privileged checkout and self-hosted rules are direct-pattern checks. Indirect checkout refs, custom checkout actions, workflow_run artifact trust, dynamic runner labels, repository defaults, environments, and organizational policies require manual review.
- YAML aliases/merges are deliberately unsupported and fail the scan. Shape checks are not a complete GitHub Actions schema validator. Anchors without aliases are accepted. Generic mode provides only secret heuristics; no native GitLab/Azure/Jenkins analysis is claimed.
- No action provenance check, remote/local action expansion, reusable workflow expansion, Git-history audit, dependency-vulnerability lookup, dependency lockfile verification, or network sandboxing is implemented. The single pinned Python dependency is not hash-locked.
- Scan results represent files read during that invocation. Use a clean reviewed checkout for a release. Reports omit configuration values, but file paths and locations are still included and may be sensitive.

## Reproduce

From the project root in PowerShell:

```powershell
.\.venv314\Scripts\python.exe -m pip install -r requirements.txt
.\.venv314\Scripts\python.exe -m unittest discover -s tests -v
.\.venv314\Scripts\python.exe auditor.py examples\insecure.yml
.\.venv314\Scripts\python.exe auditor.py examples\secure.yml --fail-on low
.\.venv314\Scripts\python.exe auditor.py .github\workflows --fail-on low
.\.venv314\Scripts\python.exe auditor.py examples\insecure.yml --format sarif --output reports\scan.sarif
```

For Linux, create a Python 3.14 venv and substitute its bin/python interpreter. This is a portability instruction, not evidence of a Linux run.
